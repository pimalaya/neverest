The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- **Queued submissions no longer fail against a server that checks the greeting.** The SMTP session greeted with `EHLO localhost`, which is not a domain name a server is obliged to believe: RFC 5321 §4.1.4 entitles it to check, and one that does (Stalwart) answers `550 5.5.0 Invalid EHLO domain`, so the session died before `MAIL FROM`. The failure is transient, so the intent stayed pending behind a warning: the queue filled and no mail ever left. The greeting is now the loopback address literal `[127.0.0.1]`, the form RFC 5321 §4.1.3 reserves for a client with no resolvable name of its own.

- **A side that may not delete no longer resurrects the item on every side.** A refused delete (`<side>.<backend>.item.delete = false`, or a side neverest does not push to) was being *undone* rather than held, which states that the side still holds the member; the shared store reads that as the item being alive and clears the deletion for every side, so removing an item once brought it back everywhere. The tombstone now stays until a run that may push delivers it. **If you configured a side to take no deletes, deletions on the other side were being reverted; they now stand.**

- **A store's disk was never reclaimed.** The store deliberately collects nothing by itself (an unreferenced body is not a deleted one: the batch that attaches a body may not be the one that indexed it), leaving reclamation to whoever owns the store, which is neverest. Nothing ran it, so every body a purge, a move or an edit dereferenced stayed on disk for ever, reported by no read and no check, while `store.purge-after` reported bytes it had merely *released* as bytes reclaimed. The retention sweep now runs the collector after a purge that took something and reports what actually left: the `--json` report's `purged` section carries `objects` beside `items` and `bytes`. A store that has been running for a while reclaims its backlog on the next sweep. Orphan blobs left by a crash are still `pimdir gc`'s to take.

- **A handle-space rebuild no longer freezes the mailbox.** An IMAP `UIDVALIDITY` bump renumbers every message, and the store read the rebuild as one server reporting each identity under a second handle: it kept the handles the server had just voided, marked every item ambiguous and stopped syncing the collection in both directions, with nothing able to clear it. Fixed in io-pimdir; a rebuild now carries the collection over as it always claimed to.

- **An identity a collection holds twice no longer costs the other side its copy.** Two messages with the same `Message-ID` in one mailbox used to pair with one another arbitrarily: deleting the paired copy propagated a delete that removed the only copy on the other side while the first side still held the message, and a later checkpoint loss revived the retained row and re-appended it, reporting `already in sync` while doing so. The engine now freezes such an identity and derives nothing for it in either direction, and neverest reports it (see Added).
- **A relayed copy is now reported.** A two-IMAP account streams a crossing body server-to-server without storing it, which never reached the projection the report is built from, so every relayed append was invisible: a run that appended messages to a server could print `already in sync`. Each relay is itemized where it happens, so `already in sync` again means the run wrote nothing.
- **A CardDAV side no longer dies after its first request.** A server that closes the connection between requests (Radicale's built-in server answers HTTP/1.0; any server may send `Connection: close`) left every exchange after the first writing into a socket the peer had hung up on, so discovery itself failed. The connection is reopened and the exchange run again, carrying the discovered principal and home-set URLs over, and only an end-of-stream or reset failure is retried, so a create or a delete is never replayed against a server that acted on it.
- **A DAV collection no longer fails its scan.** Freshly probed items were raised to the `Meta` tier whatever the kind, which asks a CardDAV side for the cheap summary tier it has none of (a `sync-collection` REPORT returns hrefs and ETags, never a `UID`). The tier is now the kind's: `Meta` for mail, `Full` for the DAV kinds.
- A body is hydrated by the absence of a stored body rather than by the item's detail level, so an item whose stale body was dropped is picked up again.

### Changed

- **BREAKING**: renamed `completions` and `manuals` to `completion` and `manual`, the plural staying as a hidden alias.
- **BREAKING**: bodies are named by the hash the **store** records (`store_meta.hash_algo`, blake3, base32 as pimdir SPEC §5 fixes it) instead of by neverest's own 128-bit FNV-1a in hex. Every consumer of one store now names the same body identically, which is what makes the object store dedup at all. An existing replica keeps its old object names and is not rewritten; a resync (`sync --reset`) is what re-lands its bodies under the recorded algorithm.
- **Every summarised item carries a `sort_key`** (pimdir SPEC §9.3), so a reader pages a collection in its natural order instead of scanning it whole: the `Date:` header in RFC 3339 UTC at seconds precision for mail (derived identically at both tiers, so hydrating a message never re-sorts it), the casefolded display name for a card. Content with nothing to derive from keeps the empty key, which the store reads as unknown.
- Every collection is grouped under the account that syncs it (pimdir SPEC §9.2), so a store shared by two hand-written accounts says whose collection is whose.
- A store an earlier draft of the pimdir format wrote is refused naming the command that fixes it (`neverest sync --reset -a <account>`), the store being a derived cache rather than something to migrate.
- Bumped the Pimalaya libraries: io-replica 0.4 (a flag set tells *unknown* from *known-empty*, a placement carries a sort key), io-pimdir 0.3 (the store owns its content hash), io-imap 0.6 and io-smtp 0.3 (their commands moved onto client traits), io-webdav 0.2, io-http 0.5, io-pim-discovery 0.7, io-msgraph 0.3 and pimalaya-stream 0.3 (its `Read`/`Write` retry a stream reporting it is not ready). SASL moved out of pimalaya-stream into the new io-sasl crate, and `io-imap/scram` is enabled so the SCRAM-SHA-256 the configuration has always offered is actually runnable. The minimum supported Rust version is now 1.89.
- The configuration wizard offers only the mechanisms the configuration can express: io-sasl names every registered SASL mechanism, and one the server advertises that neverest cannot write a config for is dropped from the menu rather than reaching an unreachable arm.

- **BREAKING**: the reserved `Outbox` collection is gone; a queued submission is now a `submit` action in the pimdir queue (see Added). Neverest no longer creates an `Outbox` collection on every run, no longer matches that name case-insensitively, and no longer hides it from collection listings, so a remote folder called `Outbox` is synced like any other one. **Anything that wrote a message into the local `Outbox` collection to have it sent must enqueue a `submit` action instead**; a message left in an `Outbox` collection is now an ordinary item, and is never submitted. The change takes a mail concept out of a store that should not hold one: submission is a capability of the engine, carried by the queue, not a collection in the store.
- The `--json` report renames the `outbox` section to `submitted`, whose entries carry the queue row id, the anchoring collection and whether the failure parked the row. The text report renames the section to `Submissions`.
- **Per-side permissions are now actually enforced per operation.** `SideCtx::writable()` collapsed the whole permission set into one all-or-nothing "may this side push at all" boolean, so `item.delete = false` (then `message.delete = false`) had no effect as long as any other permission was granted. They now map onto io-replica's per-kind push rights one to one — `flag.update` → flags, `item.update` → content, `item.create` → add, `item.delete` → remove — and a forbidden kind is kept pending by the engine while the others still propagate. **If you relied on a tightened permission block, it takes effect now where it previously did not.**
- Added the `<side>.<backend>.item.update` permission, gating in-place body edits. It defaults to `true` and is optional, so an existing configuration parses unchanged. It only bites on a mutable-content backend; mail bodies are immutable, so it is inert for IMAP and Microsoft Graph.
- The sync seam carries content revisions (ETags) end to end — enumerate, both fetch paths, and pushes — and implements conditional in-place updates: an edit is written `If-Match` the last-synced revision, and a remote that moved since is *rejected* rather than overwritten, so the engine re-merges and records a conflict instead of destroying someone's edit. Conflicts are reported (text and `--json`) as warnings, and re-reported every run until resolved; neverest never resolves one by itself. No mail backend exercises any of this — mail bodies are immutable — it is the groundwork for the CardDAV and CalDAV backends.
- The driver no longer knows what a UIDVALIDITY is: the handle-space rebuild guard reads an opaque epoch through the backend (`Client::handle_space_epoch`), and the IMAP checkpoint codec moved into the IMAP adapter where it belongs.
- **BREAKING**: the sync vocabulary is now kind-neutral, the first step of turning neverest from a mail sync into a generic PIM sync (see [`cairn/changes/generic-pim-sync/`](./cairn/changes/generic-pim-sync/)). Everything above the backend seam speaks **collections** and **items** rather than mailboxes and messages; each protocol adapter keeps its own nouns behind the seam (an IMAP mailbox is still a mailbox inside the IMAP adapter). Nothing about the sync itself changed — this step is vocabulary only.
  - Configuration: the per-account `mailbox` / `message` tables became `collection` / `item`, and so did the per-side permission tables (`<side>.<backend>.collection.{create,delete}`, `<side>.<backend>.item.{create,delete}`). **Both old spellings keep working** as serde aliases for one release, so an existing configuration loads unchanged.
  - CLI: `--include-mailbox` / `--exclude-mailbox` / `--all-mailboxes` became `--include-collection` / `--exclude-collection` / `--all-collections`, keeping the old long names as aliases and the `-m` / `-x` / `-A` short flags. Existing scripts keep working.
  - `--json` report: the `mailbox` and `email` patch sections are now `collection` and `item`, and the hunk payloads carry `collection` where they carried `mailbox`. **This one has no alias** — a consumer of the JSON report must be updated.
- **BREAKING**: the bidirectional sync engine now runs on the [`io-replica`](https://github.com/pimalaya/io-replica) replica engine instead of the hand-rolled 3-way diff/apply. Each account keeps a local replica at `$XDG_STATE_HOME/neverest/<account>/` (a JSON index plus a content-addressed blob store), each side reconciles against its server through io-replica's `sync` (checkpoints, push-outcome discipline, flag merge, object dedup), and a thin cross-merge propagates messages/flags/deletions between the two mirrors. The old `state.json` snapshot is replaced by `index.json` + `objects/` + `links.json`; re-run `init`. The design and its first-cut gaps are documented in the crate header (src/main.rs).
- **BREAKING**: full rewrite on top of the I/O-free `io-*` ecosystem (`io-email`, `io-imap`, `io-jmap`, `io-gmail`, `io-msgraph`, `io-m2dir`) plus `pimalaya-cli` / `pimalaya-config` / `pimalaya-stream`. The CLI, the configuration schema and the sync engine all changed shape; see [MIGRATION.md](./MIGRATION.md) for the upgrade path from v0.1.0.
- **BREAKING**: the SMTP submission channel moved from the account root into the side it completes: `<side>.smtp.*` instead of `smtp.*`. The channel is a property of one provider, not of the account, and whether a side needs one at all depends on its backend (Microsoft Graph sends through its own `sendMail` action, and JMAP will send by itself once its submission lands), so a table sitting beside `left` and `right` said the wrong thing. Queued submit intents are performed through the first side offering a channel, its own `smtp` table before its native send, so `left` wins on an account where both sides could send. A configuration keeping `smtp` at the root now fails to parse; move the block under `left` (or `right`).
- Bumped `pimalaya-cli` and `pimalaya-config` to `0.1` (the wizard's secrets distinguish an argv command from a shell command line) and `io-pim-discovery` to `0.4` for the wizard's bounded parallel discovery. (The backend crates `io-imap`/`io-jmap`/`io-gmail`/`io-msgraph`/`io-http` and `pimalaya-stream` stay pinned by the frozen `io-email 0.1`; moving them further needs the `io-email` removal / protocol-direct migration.)
- Relicensed from `AGPL-3.0-only` to `MIT OR Apache-2.0`, aligning with the rest of the Pimalaya ecosystem.
- The pimdir store schema (draft v1) includes the action queue and collection generations; a store stamped with a newer schema version than the binary understands is refused on open (the spec is a draft: such a store is recreated, never migrated).
- Every remote is now a cargo feature, matching the pre-existing `imap` one: `msgraph` gates the Microsoft Graph backend and `smtp` gates the SMTP submission channel queued submit intents are performed through. All three ship in the default feature set, so a default build is unchanged. Every side config still parses in every build and every unavailable backend fails at runtime rather than at build time: opening a side whose backend was not compiled in reports it, exactly as the JMAP and Gmail sides already did, and a build with no send channel leaves queued submit intents pending and warns instead of performing them.
- The configuration wizard now opens with a welcome banner and asks for a single input, an email address (the account name is derived from its domain instead of being prompted). Discovery runs every mechanism in parallel (fixed provider rules, PACC, Thunderbird Autoconfiguration, RFC 6186 SRV) under an 8 second deadline rather than trying them in series and keeping the first non-empty answer, and every reachable service is proposed as a selectable configuration. Only backends compiled into the running build are offered, so the wizard can no longer write a side that fails to open: IMAP (plus the SMTP send channel when a submission server was discovered, reusing the IMAP login and password on confirmation) and, on a Microsoft account, the Graph API. The IMAP mechanism list is narrowed by an unauthenticated CAPABILITY probe, secrets are collected through the shared keyring and OAuth-broker pickers (so the generated config reads them from a command), and every configured connection is tested before the file is written. The wizard writes a one-side (local sync) account only: a remote-to-remote mirror stays hand-written. `neverest configure` runs the same flow over an existing account, seeded with its current email, and preserves the `default` flag, store, mailbox, message, connection settings and any `right` side. A bare `neverest` (no command) runs the wizard too, like a bare `himalaya`, instead of erroring out on the missing subcommand; the generated configuration is offered for saving (never overwriting an existing file without confirmation) and printed on stdout when you decline, and `--json` or a redirected stdout skips the prompts and emits the document, so `neverest > config.toml` writes the file itself. The generated document renders like himalaya's: the account name is the only table header, every field below it is a dotted key, and defaulted values (side permissions, pool size, collection filter, ALPN, `starttls`, a non-default flag) are left out, so what lands on disk is only what the wizard actually decided.
- The IMAP and SMTP `alpn` config fields are now optional rather than defaulted in place, so io-imap and io-smtp own their own default (`["imap"]` and `["smtp"]`). Leaving `alpn` unset takes that default, `alpn = []` still skips ALPN. The SMTP submission channel therefore now offers the `smtp` ALPN token (RFC 7595) where it previously offered none; set `<side>.smtp.alpn = []` to restore the old behaviour.

### Added

- **A warnings section for an identity a collection holds twice**, in the text report and under `ambiguous` in `--json`, naming the collection and every id involved (*2 copies of one item in `INBOX` on right (`145`, `146`)*). It is re-reported on every run until the collection holds the identity once, since the state that makes it visible is persisted rather than rediscovered: a second copy appears in exactly one enumeration. Neverest repairs nothing and blames nothing: which copy to keep is the user's call, with their own client, and the wording says what neverest cannot tell apart rather than that the mailbox is invalid. Detection, the derive-nothing rules and the persistence live in io-replica and io-pimdir.
- **CardDAV** backend support via [`io-webdav`](https://github.com/pimalaya/io-webdav), behind the new `carddav` cargo feature (out of the default set until its live suite runs in CI). Address books are collections, keyed by their path segment rather than their display name (a display name is optional, mutable and free to collide, none of which a collection key survives). Enumeration is RFC 6578 `sync-collection`, the server's token riding as the engine's opaque checkpoint: a rejected token falls back to a full report, and a truncated one is drained. Bodies come from `addressbook-multiget`, and writes are `PUT` / `DELETE` conditional on the last-synced ETag.

  This is the first **non-mail** kind and the first **mutable-content** backend, which is what makes it more than one more protocol. Cards are edited in place, so it is the first backend to exercise the revision plumbing, the conditional-write path and the conflict handling that mail (whose bodies are immutable) leaves inert: a card edited on both sides is now genuinely reported as a conflict and left alone rather than overwritten. A card resolves at the `Full` tier only, since a `sync-collection` REPORT carries hrefs and ETags but no `UID`, and CardDAV has no flags, so every card reports a known-empty flag set rather than an unknown one.

  A card's link id is its vCard `UID` (`uid:`), falling back to an FNV-1a digest of the body (`hash:`) for a card carrying none, and its `v:1` summary carries the `UID`, `FN` and every `EMAIL` so a reader renders a contact list without fetching bodies. Cards cross neverest as opaque bytes: the scanner reads those fields and never rewrites a card, so a property it does not understand cannot be lost.

  A contacts account pairs with another contacts side or with the store alone: the two sides of an account must agree on their kind, and an `<side>.smtp` table on a DAV side is refused (submission is a mail capability). The wizard offers a discovered CardDAV endpoint (RFC 6764) beside the mail ones when the feature is compiled in.
- **JMAP** backend support via `io-jmap`.
- **Gmail** backend support via `io-gmail` (Gmail REST API, OAuth 2.0 bearer token).
- **Microsoft Graph** backend support via `io-msgraph`: delta-query enumeration (the `@odata.deltaLink` as the sync checkpoint, an expired link restarting a full round), bodies via the raw MIME endpoint, and flag and delete pushes (`message_update` / `message_delete`; appends and moves into Graph are pull-only). Authentication is a bearer access token only, resolved through the standard secret-command idiom (`auth.token.raw` / `auth.token.command`); neverest runs no OAuth flow itself, the whole OAuth setup (device sign-in, client credentials, certificates, token refresh) is delegated to an external command, typically `ortie`.
- Reintroduced the per-account `sync.lock` advisory file lock so two concurrent `sync` runs (cron tick racing a manual invocation, two terminals) no longer corrupt the cache snapshot; the lock now lives in the actual store directory (honouring `store.root`) and a second run waits up to 60 seconds for the holder before exiting with a clear error, so cron ticks and connector-triggered scoped runs serialize.
- Neverest is now the pimdir store's sole owner: every sync run first drains the store's action queue (mutations a frontend enqueued through io-pimdir's producer surface), applying each action exactly-once and reporting per-collection applied counts plus any parked (permanently unappliable) action until repaired; the sync then pushes the resulting dirty state.
- Added the queued **`submit` intent** and its send channel: a frontend enqueues a submission through the store's action queue (one `v: 1` JSON payload naming the body blob as `object`, plus the `from` / `rcpts` envelope; the queue row pins the body until the send), and every run performs the pending ones through the first side offering a send channel, its own `<side>.smtp` table (SMTP submission, `smtps://` or `smtp://` + `starttls`, optional login) or its native send (the Graph sendMail action). A sent intent is acknowledged, which releases its body; an SMTP 4xx (or a broken connection) leaves it pending for the next run and an SMTP 5xx parks it with its error, so nothing is resent forever and nothing is silently dropped. A build with no send channel leaves the intents pending rather than parking them. Submission is at-least-once: a crash between the server's acceptance and the acknowledgement resends, so deduplication is the receiving provider's job (`Message-ID`).
- Added `store.purge-after`, the retention sweep. A pimdir store retains an item instead of deleting it when its last binding vanishes (hidden from the sync and from listings, body kept); after each sync neverest purges every retained item older than this human delay (`"90d"`, `"12h"`, `"0"`) and reports the items and bytes it reclaimed, in the text and `--json` output. **Unset means never purge**, `"0"` reproduces a terminal delete, and `sync --no-purge` skips the sweep for one run. Combined with a read-only remote side (`<side>.<backend>.item.delete = false`, `collection.delete = false`) it makes a backup a remote expunge cannot lose.
- Added the IMAP handle-space rebuild: a backend UIDVALIDITY change detected across a pull drives io-replica's rekey (cached bodies, summaries and pending state carried over by link id) and bumps the collection's `generation` atomically with the rebuild through `write_rekeyed`, so a store frontend derives its epoch from the store alone. Graph sides never bump (message ids survive delta resets).
- Added `store.hydration = "full"`: a two-source retain sync mirrors every body into the store instead of only the crossing ones (the gateway deployment); the default stays per-mode.

### Removed

- **Collection aliases** (`collection.alias`, the v0.1 `folder.aliases`). The table parsed and nothing ever read it: substituting a friendly name for a backend id is display work, and neverest renders nothing. The store already carries per-collection display metadata (`name`, `color`, `description`, `sort_order`) for the frontend that does. A configuration still declaring the table is now refused rather than silently ignored.
- **Notmuch** backend (no replacement in the `io-*` ecosystem yet).
- **Local file backends as sync sides** (Maildir, then m2dir). A side is a remote; the pimdir store *is* the local replica, so a local file store beside it would be a second local copy. An existing on-disk tree is brought in through io-pimdir's conversion tooling instead.
