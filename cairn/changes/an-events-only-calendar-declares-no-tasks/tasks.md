## Notes

- The regression test is src/offline/driver.rs `an_events_only_calendar_refuses_a_task_before_it_is_queued`: with the `x-vtodo` rows left out of `declare`, the add into `caldav/events` is queued and the test panics at its "refused at the gate" assertion.
- The gate reads the sources syncing a collection (a `sources` row or a binding, io-pimdir `load_capabilities`); since 2026-10-29 a listing writes that row (src/offline/storage.rs `register_syncing`), so a calendar recorded by `sync --declare-only` refuses a task before its first sync.
- The tests of the extension, all in a scratch store with no server: src/offline/driver.rs `a_google_or_graph_calendar_refuses_a_task_before_it_is_queued`, `a_target_s_events_only_calendar_refuses_a_task_before_it_is_queued`, `a_google_target_keeps_the_source_s_calendars_from_tasks`, `a_calendar_met_mid_run_is_gated_from_its_first_item_sync`; src/cli/check.rs `a_check_reports_the_calendars_that_take_no_tasks`, `a_check_names_what_each_calendar_takes`; src/offline/capability.rs `a_provider_keeping_tasks_apart_declares_none_source_wide`.
- Regression proof (2026-10-29), on `git archive HEAD` (474753d) in a scratch copy: the Google/Graph, Google target and check-capability tests call `declare` and `supports` as they stand there and fail (the task is queued, `Ok(1)`; no `x-vtodo` row in the check). The seams the other tests call did not exist, so the copy took shims holding the old behaviour at each: `record_listing` as run_local recorded the listing and named the collections, with no declaration (fails: `accepts_vtodo("caldav/events")` is true after the first item sync); `record_pair_listing` doing nothing, as run_pair recorded and declared nothing (fails: the task is queued); `checked` building the old `CheckedCollection` (fails: no `takesTasks` key). The capability unit test calls `vtodo_wide`, new, and has no old counterpart.
- Provisional (check): `neverest check` reports what the configuration and the listing state, not the store's rows: the source-wide `x-vtodo` row joins the capabilities (a Google or Graph calendar source, or a source copied to one), and a CalDAV calendar's statement is `takesTasks` on the collection, on a target's collections too though a sync declares it on the source. A check opening no store cannot verify the declaration itself; reading the rows back (`PimdirReader::capabilities`) would make the doctor depend on a sync having run.
- Provisional (targets): with targets the source carries the rows, a target staying undeclared: declaring a target with an `x-vtodo` row alone would make it a declared source refusing every Annex B capability it has no row for. A Google or Graph calendar target makes the source's row source-wide, every calendar of the source being copied there.
- Provisional (targets, record): a run that stops before every target of the source has listed adds what it listed to the record and keeps the rest; one where every pair listed replaces it. A calendar a pair creates on the other endpoint this run is known by the listing of the endpoint that had it, the created one's own component set (the server's default) read at the next listing.
- Provisional (discovery): a listing declares the account again before any item moves (local: after the collections are recorded; paired: after every common collection is named, which run_pair now does before its sync loop rather than per collection). A failure there is logged, the declaration before the drain standing. The sidecar is still saved at the end of the run only, so a run that crashes between a listing and its end leaves rows in the store that the next run's first declaration drops until it lists again.
- Closed (was Open, io-pimdir): a calendar listed but not yet synced refused no task, the gate reading only sources with a row or a binding there. No io-pimdir change was needed: a `sources` row with a NULL checkpoint already counts (pimdir checks/invariants.sh, "by its checkpoint alone") and reads as no sync state, so neverest writes one at the listing through the canonical statements on a connection of its own (io-pimdir exposes no owner write for it; `io_pimdir::sql` vendors them for that), as Android's `EventStore.ensureSynced` does.
- The registration tests, in a scratch store with no server: src/offline/driver.rs `a_listed_calendar_refuses_a_task_before_its_first_sync` (a calendar outside the home set, id `/caldav/v2/x%40g/events`), `a_listing_keeps_the_checkpoint_a_source_holds`, `a_pair_s_listed_calendar_refuses_a_task_before_its_first_sync`.
- Regression proof of the registration (2026-10-29), on a scratch copy of the working tree before it (the io-pimdir and io-webdav pins applied), the tests grafted in: `a_listed_calendar_refuses_a_task_before_its_first_sync` and `a_pair_s_listed_calendar_refuses_a_task_before_its_first_sync` fail (the task is queued, `Ok(1)`), `a_listing_keeps_the_checkpoint_a_source_holds` fails (`collection_sources` is empty). Shim: `record_pair_listing` took a `common` it ignored, the old code registering nothing.
- Provisional (registration): every kind is registered, not calendars alone, a row with no checkpoint being no state to the engine; in a pair only the source is, the target staying unrecorded as it stays undeclared, so the collection diff's base (`held_by_both`, both endpoints holding a row or a binding) is unchanged unless the target already held one. A registration failure is logged, the first item sync writing the row anyway. neverest now depends on rusqlite 0.40 directly, the crate io-pimdir links (one build, `vendored` reaching it through io-pimdir), for that one write.
